**MBTI × 感情分析レコメンド「TYPECAST」を Go / React / Gemini で構築した技術的知見**

---

## はじめに

「映画を観ようと思ってNetflixを開いたのに、作品を選んでいるうちに疲れ、結局YouTubeを見て寝る」という経験は、多くのユーザーに共有されうるものである。筆者も同様の経験をほぼ毎回している。

「今の自分の気分」と「自分の性格（好み）」を適切に理解したうえで、**「今日はこれを観よ。なぜなら君はいま、こういう状態だから」** と論理的に説得してくれる存在への欲求が、本サービスの動機となった。

その欲求から生まれたのが、**MBTI × 感情分析シネマレコメンドアプリ『TYPECAST』** である。

- **サービスURL**  
  `https://tycast.net/`

- **サービスの概要**
  - MBTI（16タイプ）と、現在のMood（気分・悩み）を入力する
  - バックエンドで Gemini が心理機能と心理状態を解釈する
  - **「なぜその映画なのか」の理由付きで、映画を3本レコメンド** する

本稿では、現行リポジトリ（Go/Echo + Cloud Run、React/Vite + Firebase Hosting、Firestore、Gemini、TMDB）をベースに、実装において特に問題となりやすかった以下の点に絞って述べる。

- **Geminiへの人格埋め込み（プロンプト設計と扱い方）**
- **SPAにおいて「動的OGP」を成立させるためのバックエンド構成**
- **Secrets / 環境変数の保持とデプロイフローへの組み込み**

## プロダクトの特徴

TYPECASTは、「当てにいく診断」ではなく、**「納得感のある理由付きレコメンド」** に特化したサービスである。

- **理由付きレコメンド**
  - 例として「INTPは抽象概念の整合性や思考実験に快感を得やすい」といった、MBTIの心理機能（主機能 / 補助機能）を根拠に、**そのユーザーに刺さりうるポイント** を説明する。
- **Moodの感情分析およびスコア化**
  - ユーザーが入力したテキストを Gemini で感情分析し、スコアやカテゴリを算出する。
  - 過去1週間分の Mood 推移をチャートで表示し、「最近の自分の状態」を振り返れるようにしている。
- **1日N回までの利用制限（β運用）**
  - レコメンドはコストが読みづらいため、`DAILY_RECOMMEND_LIMIT`（デフォルト3〜5回）で制御している。
  - ユーザー単位で回数をカウントし、**βテストでも安心して運用できる設計** とした。
- **Xシェア対応の動的OGP**
  - 診断結果をシェアすると、**映画タイトル・Mood・スコアを含むOGP画像** を動的生成する。
  - 「結果を貼るだけで、どんな診断であったかが一目で伝わる」体験を狙った。

## 全体アーキテクチャ（モノレポ構成）

リポジトリは、**フロントエンドとバックエンドを同一リポジトリに置くモノレポ構成** である。

- **Frontend**
  - React + Vite + TypeScript
  - Firebase Hosting でホスティング
  - Firestore / Firebase Authentication と連携
- **Backend**
  - Go + Echo
  - Docker コンテナ化のうえ Cloud Run にデプロイ
- **Auth / DB**
  - Firebase Authentication
  - Firestore（ユーザー、履歴、シェア情報を保存）
- **AI**
  - Gemini API（`gemini-2.0-flash`）
- **Movie Data**
  - TMDB API（作品情報の取得）
- **CI/CD**
  - GitHub Actions
    - Cloud Run へのデプロイ（バックエンド）
    - Firebase Hosting へのデプロイ（フロントエンド）

**1リポジトリで完結** させることで、

- Cloud Run / Firebase Hosting の設定を **GitHub Actions に集約** できる
- 「とりあえずこのリポジトリを clone すれば全体を追える」状態を実現できる

という利点がある。

## TIPS①：Geminiに「人格」を埋め込む（プロンプトは環境変数で管理）

TYPECASTの核心は、**「MBTIに基づく納得感のあるコメントを返す」** ことにある。単に映画を3本返すだけなら任意のLLMでも実現可能だが、本システムでは Gemini に対し、

- **心理学と映画理論に詳しいコンシェルジュ**
- **MBTIの心理機能を理解している**
- **レスポンスは JSON のみを出力する**

という人格・役割を付与している。

ここで重要なのは、

- **レスポンス形式を JSON に固定し、Go 側で安定してパースすること**
- **そのプロンプト（人格設定）をコードに直書きしないこと**

の2点である。

### JSON固定：`ResponseMIMEType` の指定

Geminiのレスポンスが自然文とJSONの混在になると、Go でのパースが不安定になりやすい。

そこで、クライアント生成時に

- **`ResponseMIMEType = "application/json"`**

を設定し、**「JSON以外を返さない」という約束をAPIレベルで固定** している。

これにより、

- 文章の後にJSONが続いてパーサーが失敗する
- 余計な説明文が混入する

といった事象が減少し、「LLMまわりのデバッグに時間を取られる」リスクを抑えられた。

### プロンプトの `GEMINI_PROMPT_TEMPLATE` 環境変数による注入

人格を定義するプロンプトはリポジトリには置かず、

- **`GEMINI_PROMPT_TEMPLATE` という環境変数に格納**
- GitHub Actions（Cloud Run デプロイ時）やローカル `.env` から注入

する方式を採用した。

運用上のポイントは以下のとおりである。

- **改行は `\n` を含む文字列として環境変数に格納する**
  - Go側で `strings.ReplaceAll(template, "\\n", "\n")` により復元する
- `fmt.Sprintf` のプレースホルダに差し込む情報
  - MBTIタイプ
  - 心理機能の説明
  - ユーザーのMoodテキスト
  - 除外したい映画タイトル（既視聴・好みでないなど）
- CI / ローカルで容易に差し替え可能にしておく

この形にしておくことで、

- 「プロンプトのみ微調整したい」という場合に、**コードを変更せず環境変数の更新だけで改善** できる
- プロンプト自体（≒ノウハウ）をリポジトリに露出させずに済む

という利点がある。

## TIPS②：SPAでも「動的OGP」を成立させる（Bot判定 + OGP HTML + 画像生成）

React/Vite のような SPA では、一般に

- どのURLにアクセスしても `index.html` を返す
- OGPタグもビルド時に固定

という構成になりがちである。しかしこのままでは **X（旧Twitter）のクローラーはJSを実行しないため、OGPが正しく取得されない**。

TYPECASTでは、**バックエンド（Go）側でクローラーを検知し、OGPタグ付きのHTMLを返す** ことでこれを解決した。

### 1. シェアの全体フロー

TYPECASTのシェア機能は、おおまかに以下の流れである。

1. フロントで「シェア」ボタン押下  
   → `POST /api/share` に、映画タイトル / Mood / スコアなどを送信する
2. バックエンドで Firestore に保存し、短いID（UUIDの先頭8文字など）を発行する
3. レスポンスとして `share_url`（例: `https://tycast.net/s/:id`）を返す
4. ユーザーがXにURLを貼る
5. Xなどのクローラーが `GET /s/:id` にアクセスする
6. バックエンド側で User-Agent を参照し、
   - **Botである場合**: OGPメタタグを含むHTMLを生成して返す  
     - `twitter:image` には `GET /api/ogp?...` のURLを設定する
   - **人間のブラウザである場合**: フロントのルートへリダイレクトする  
     - 例: `FRONTEND_URL?share_id=:id`

このようにすることで、

- クローラー → OGP専用HTML
- 人間 → 通常のSPA

という2経路を、1つの `/s/:id` エンドポイントで扱えるようにしている。

### 2. 簡易なBot判定（User-Agent）

Bot判定は、実用上の必要十分性を満たす範囲でシンプルに実装した。

- `User-Agent` を lower-case に変換する
- `twitterbot`, `slackbot-linkexpanding` などの文字列を含むかどうかで判定する

ハッカソン用途であれば、**この程度の簡易実装でも実用上は十分** であった。

### 3. OGP画像生成エンドポイント（`/api/ogp`）

OGP画像自体は、別エンドポイントで PNG を動的生成している。

- `GET /api/ogp?title=...&mood=...&score=...`
- レスポンス: `image/png`

実装には **`fogleman/gg`** を用いた。

- GoでCanvasライクに描画できるライブラリである
- テキスト描画・背景・簡単なレイアウトを簡潔に記述できる

#### 注意点：フォント / 静的アセットはバイナリに自動では含まれない

ローカルでは問題なく動作していたが、Cloud Run にデプロイすると失敗する──  
TYPECASTでは、その原因が **フォントファイルの読み込み** であった。

- 画像生成時に `assets/fonts/Bold.ttf` を読み込んでいる
- しかし、Dockerイメージに `assets/` をコピーしていないと、本番環境ではファイルが存在しない

そのため、Dockerfileでは

- **ビルドステージ** でGoバイナリをビルドする
- **実行ステージ** にバイナリと `assets/` ディレクトリをコピーする

という形で、**実行イメージにフォントを同梱** している。  
OGP付きのサービスをCloud Runで運用する場合、この点は重要な注意点である。

## TIPS③：Secrets / 環境変数の扱いとデプロイ戦略

最後に、**公開できない情報（APIキー・URLなど）の扱い** について述べる。

TYPECASTでは、以下の情報を **GitHub Secrets** に集約し、**デプロイ時に環境変数として注入する** 方針を採用した。

- **Gemini / TMDB のAPIキー**
- **Firebase / Firestore の接続情報（Project ID, DB名）**
- **`FRONTEND_URL` / `API_BASE_URL`**（OGPリンク生成やフロント→API通信に必要）

### バックエンド（Cloud Run）への環境変数注入

GitHub Actions から Cloud Run にデプロイする際、

- `gcloud run deploy ... --set-env-vars ...`

を用い、Secrets から取得した値を環境変数として渡している。

特に重要であったのは **`FRONTEND_URL` と `API_BASE_URL` を Cloud Run 側で明示すること** である。

- これを誤ると、OGPやリダイレクト用のURLが `localhost` のままになることが多い
- 実際に、本番環境で `localhost` のURLが埋まったOGPを出力してしまい、修正を要した経験がある

ハッカソンなど短期開発では、**URL系の環境変数はチェックリスト化しておくことが望ましい**。

### フロントエンド（Vite）の環境変数

Viteは、ビルド時に `VITE_` プレフィックスの付いた環境変数を埋め込む。

- 本番では CI のビルドステップで `VITE_API_URL` などを `env:` に渡す
- Firebase Hosting にデプロイされるバンドル内に、その値が焼き込まれる

ここを誤ると、

- 本番フロントエンドがローカルAPIを叩く
- あるいは存在しないエンドポイントにリクエストしてしまう

といった事象につながるため、**「本番用 `VITE_API_URL` がどのエンドポイントを指しているか」をデプロイ前に毎回確認する** 運用とした。

## 補足：β運用における「1日N回レコメンド制限」

LLMを用いたレコメンドは、コストもレスポンスタイムも予測しづらい側面がある。

TYPECASTではβ運用として、

- `DAILY_RECOMMEND_LIMIT`（デフォルト3回程度）を設けた
- Firebase Authentication のユーザーIDごとに、当日の利用回数をカウントする
- 上限に達したら、その日はレコメンドを拒否する

というシンプルな仕組みを導入した。

これにより、

- 「一部のユーザーだけが大量にリクエストする」リスクを抑制できる
- ハッカソン本番中にクラウド費用を気にせず運用できる

という意味で、**運用上の負荷を軽減する** 効果があった。

TYPECASTはまだβ的な位置づけであるが、今後は以下のような方向で拡張を検討している。

  - TMDBから収集した映画情報をベクトル検索可能な形で保持する
  - Geminiに「根拠付き」で渡すことで、**幻覚の少ないレコメンド** を目指す
- **VOD連携の強化**
  - 「どこで視聴できるか」まで含めて提示し、ユーザーが **“選んだあとに迷わない”** 状態まで導く

## まとめ

TYPECASTは、**MBTI（心理機能）と現在のMoodテキスト** を入力とし、Gemini が心理学コンシェルジュとして **理由付きで映画を提案する** サービスである。

実装面で特に有効であった点は以下の3つである。

- **人格プロンプトをコードに直書きせず、環境変数テンプレートとして管理したこと**
  - `ResponseMIMEType = "application/json"` でレスポンス形式を固定しつつ、`GEMINI_PROMPT_TEMPLATE` によりプロンプトの改善をコード変更なしで行えるようにした。
- **SPAでもOGPを成立させるための「Bot判定 + OGPタグHTML + PNG動的生成」**
  - `/s/:id` でクローラーと人間を分岐し、`/api/ogp` でOGP画像を生成する構成により、Xシェアとの整合性を確保した。
- **SecretsをGitHub Actionsから安全に注入し、「本番URLを誤らない」運用に寄せたこと**
  - `FRONTEND_URL` / `API_BASE_URL` / 各種APIキーをGitHub Secretsで一元管理し、Cloud Run / Vite の両方に正しいURLを渡すフローを構築した。

「LLM × MBTI × 映画レコメンド」の組み立て方に関心がある読者は、実際にサービスに触れてみることを推奨する。

`https://tycast.net/`
